# Agent Note: 官方工具集不可裁空 ---- 上游按[工具集完整性]判第三方客户端

Status: implemented

## Problem

2026-10-06 用户报[升级到 2.6.0 后上游全部空响应]. 远程日志实证:

```
official channel: rpc result   status: 503  ok: false
upstream chat non-ok           status: 503  body: ""
```

body 为空 ---- 上游回了 503 但**响应体是空的**, 没有任何可读原因. 排查方向本来有三条:
模型额度用尽(旧结论 docs/reverse/07-503-root-cause.md), 出口被判受限国家, 请求形态不合法.

排除第一条: 直连 /v1/models 看到 m-096e75164d 是 recent=1 limit=6 ---- 额度没用满.

排除第二条的充分性: 日志里确实有 session admitted on limited tier ... reason:
recent_limited_country, countryCode: US 与 proxies 为空, 但那是**长期存在的环境**,
不是本次升级引入的变量.

## Decision

**用单变量对照直打远程, 一次只改一个变量**(全部走用户给的 API Key, 不带 tools 与带 tools 各一次):

| 出站 tools | 结果 |
|---|---|
| 无 tools | **200** |
| 只带 bash(下游私有名) | **503** |
| 只带 run_terminal_command(官方名, 单个) | **503** |
| **完整官方 37 工具** | **200** |

结论: 上游按**工具集完整性**判第三方客户端 ---- 出站**少一个官方工具就 503**.

而 2.6.0 引入的变量恰好命中这一点: 用户在控制台把官方工具**全部取消勾选**, 于是
officialToolNames: []. 同时本轮把 reuseChat / actReuse 的[逐项挑字段]改成展开透传, 修复了
[配置不生效]的缺陷 ---- 两件事叠加的净效果是: **一个必然失败的配置第一次真的生效了.**

修复两条:
1. **后端兜底**: selectOfficialTools 把空数组当成[未配置], 回落成全注入. 判据: 下拉到 0 个这个
   能力没有存在价值 ---- 它只会制造一个必然被上游拒绝的配置.
2. **前端显式警告**: 勾成空时在卡片上红字写出[上游会因工具集不完整拒绝请求(503), 此配置不生效].

## Alternatives considered

**什么都不做, 只在文档里写[别把官方工具全取消].** 否决: 用户原话是[你要有明确的错误, 并且在我们
这边的平台这里能显示出来, 不然我根本就不知道有这个问题]. 只在文档里写等于没写.

**让空数组继续生效, 但在 503 时自动重试一次[全注入].** 否决: 事后重试要用户先吃一次失败(且 503 是
上游明确拒绝, 重试等于二次浪费). 在配置入口就把必败配置拦掉更省事, 也不引入新的重试路径.

**把[全不注入]做成合法的排障开关.** 否决: 它没有任何正向用途. 我们需要控制的是[注入哪些],
而[一个都不注入]在上游判据下不存在可用场景 ---- 保留它只是留了个坑.

**只做后端兜底, 不做前端警告.** 否决: 用户会以为自己配的东西生效了(实际被兜底覆盖), 这比报错
更难理解. 前后端口径必须一致: 后端拦下, 前端说清.

## Consequences

- 空数组不再能裁空官方工具集; mode: 'none' 实际已不可达(类型保留以兼容旧调用点).
- 前端官方工具卡多一条红字警告(class official-tools-danger).
- 系统提示词页新增[工具判据]健康横幅, 把[当前配置会不会被上游拒绝]**显示在页面上**
  (判据: empty_official_toolset / zero_injected). 此前该判据只在 legacy 通道写日志, 而实际走的
  是 official 通道 ---- 所以用户在日志里根本看不到.
