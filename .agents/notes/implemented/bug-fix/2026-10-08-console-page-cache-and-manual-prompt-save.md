# Agent Note: 控制台页面缓存 + 系统提示词手动保存 + 账号池单一数据源

Status: implemented

受影响代码: `dashboard/views/shell/index.ts`, `dashboard/views/proxy/index.ts`,
`dashboard/views/proxy/inject/system-prompt.ts`, `dashboard/app.ts`,
`dashboard/locale/dict/system.ts`

## Problem

用户报三个问题, 实测确认根因是同一个机制(切页即整页重建):

1. 每次加载 / 更新 / 切换页面都重新渲染表单. 原实现是 `view.innerHTML = ''`
 再重新拉 2-4 个接口重建整个页面. 后果: 表单里改了一半的值被清掉;
 切回来先空一下; 提示词编辑器(Monaco)每次重挂(慢且丢光标).
2. 账号页缓存不统一 ---- 同一账号池在不同页显示两套数字.
3. 系统提示词是自动保存(800ms 防抖), 用户不知道到底生效没有.

第 2 条的根因不是缓存层, 而是[两个页面各写一份全局状态]:
`dashboard/views/proxy/index.ts` 渲染时自己拉 `/api/overview` 并覆盖
`state.accounts`, 而账号卡刚被一键刷新更新到更新的版本 ----
覆盖等于把新值按回旧值, 于是设置页与总览页显示两套口径.

## Decision

[页面级 DOM 缓存 + 账号池单一数据源 + 提示词手动保存.]

### 1) 页面级缓存: 切页只切可见性, 不拆 DOM

`shell/index.ts` 为每个路由建一个 `route-panel` 容器, 全部挂在内容区里,
切页只改 `hidden`. 于是输入框的值, 滚动位置, 展开状态, Monaco 编辑器全部保留,
也省掉每次切页重拉接口的等待. 标准 SPA 行为.

缓存失效只有两条路(刻意收窄): `invalidateViewCache()`(账号增删 / 重连 /
登出 / 骨架重建)与页面自己的 `need('render')()`. 不做 TTL, 也不做"切回来就
重拉"---- 各页本来就是靠自己的局部刷新把数据更新到最新, 整页重建从来不是
它们的数据通路.

### 2) 账号池单一数据源

`views/proxy/index.ts` 不再用自己拉的 overview 覆盖 `state.accounts`;
推荐值改用模块级 `lastPoolRows`(只读快照). 全局账号状态只由账号卡维护 ----
这是"同一屏两套数字"的根治, 而不是给缓存加一层.

### 3) 系统提示词改手动保存

去掉防抖自动落盘, 加[保存]按钮(未保存时可用, 保存后禁用)+ 状态栏显示
"已保存 HH:MM:SS". 用户明确要的是"能确认生效没有" ---- 自动保存恰恰让这件事
无法确认. 切页时若有未保存改动会拦一下(`confirm`), 因为编辑器里可能是很长的
正文, 丢了就是白改; 其余页面的输入框随 DOM 缓存保留, 不需要拦.

## Alternatives considered

- [保留整页重建, 只在重建前把表单值存起来再回填.] 最强理由: 改动面小,
 不用碰路由与缓存. 否决原因: 回填的是"输入框的值", 而页面里还有滚动位置,
 折叠状态, Monaco 光标与 undo 栈, 下拉是否展开 ---- 逐个保存与恢复是一张
 只会越来越长的清单, 而缓存 DOM 一次性解决全部. 而且重建带来的接口等待
 也消不掉.

- [缓存加 TTL(例如 30 秒后过期重拉).] 最强理由: 避免显示过期数据,
 比"永久缓存"更保守. 否决原因: 本仓已有明确的"零自动探测"纪律 ----
 数据只在用户主动刷新时更新. TTL 会让页面在用户没操作时突然自己变一次,
 那既不是缓存也不是刷新, 语义最难解释. 显式失效点比时间驱动更可预测.

- [把自动保存改成[防抖 + 显式保存按钮]并存.] 最强理由: 两种用户都能满足,
 不丢自动保存的便利. 否决原因: 用户的原话是"这样我不知道有没有生效" ----
 并存时"到底哪个生效"依旧不可判定, 状态栏会出现两套来源互相覆盖.
 手动保存的语义是唯一确定的.

- [给设置页也维护一份自己的账号快照, 谁也不覆盖谁.] 最强理由: 两页解耦.
 否决原因: `state.accounts` 是跨页共享的账号视图(logs 页也读它),
 两份快照就是两个真相; 正确的做法是让写入口只剩一个.

- [什么都不做, 只加一句[改动会在离开页面后丢失]的提示.] 最强理由: 零风险.
 否决原因: 那等于把框架缺陷转成用户负担 ---- 用户要的是"局部刷新",
 而这本身是标准 SPA 就该有的行为.

## Consequences

- 切页不再重新拉接口, 表单与编辑器状态保留; 首次进某页仍会渲染一次.
- 账号增删 / 重连 / 登出后必须清缓存(已接线), 否则会显示旧账号.
- 提示词保存从[自动]变[手动]: 忘点保存就丢改动, 因此加了切页拦截.
- 前端 checkJs 错误从基线 51 降到 48(顺手修掉 listeners 直接把 Event 当选项传的
 类型错, 以及 `soft.length` 那类遗留).
