# Agent Note: 数据文件自检搬进独立的「系统」页

Status: implemented

## Problem

控制台首屏（总览）除了日常要看的账号池 / 额度 / 请求分布 / 代理 / 模型管理，还塞进了
一整张"数据文件自检"表（每个 JSON 的装载状态 + 处置命令）。它只在**排障**时才有用，
日常却占据首屏注意力，而且每次打开总览都会多打一次 `/api/system/data-status`。

同一张表还有两个说不清的地方：`sessions.json` 里挂着待清理的会话句柄时它显示
"正常"，用户没有任何地方能看到"还有几条没结算"；而它给出的处置命令是统一的
`mv <file> <file>.broken` —— 对 `sessions.json` 这种真源文件，照做就等于永久丢掉
寻址 DELETE 的能力。

## Decision

- 数据文件自检搬到 **admin 专属的「系统」页**（`nav` 里的 `system` 路由 →
  `renderSystem`），总览不再渲染它；接口 `/api/system/data-status` 原样保留
  （它本来就要求登录，且会话是任意角色都能拿到的）。
- 表格新增一列语义：`sessions.json` 显示「待结算 ×N」（来自 `openHandles`，
  见 startup-path-bounded 那篇），并在说明里点明"不是故障、会继续清、不要手工删"。
- 「处置」列对 `CRITICAL_DATA_FILES`（`users.json` / `sessions.json`）不再给
  可直接复制的 `mv` 命令，改为提示"先备份再移走（真源文件，删了就找不回）"。
- 所有指向该功能的文案（`bin/serve.js` 的启动横幅、`docs/deployment.md`）
  从「总览 → 数据文件自检」改成「系统 → 数据文件自检」。

## Alternatives considered

- **留在总览、折叠成 `<details>`** — 改动最小，仍然一眼可见。但折叠只解决"占位置"，
  不解决"排障工具与日常面板混在一起"，而且首屏那次多打的请求还在；`<details>` 里
  的用户是真源文件，误删后果不变。
- **做成弹窗 / 只在有问题时才显示** — "只在有问题时显示"恰恰是最坏的形态：数据文件
  坏掉的表现之一就是服务起不来，那时用户连控制台都打不开；而"平时看不见"会让
  用户根本不知道有这个排障入口。弹窗则需要先点开才知道有没有问题。
- **什么都不做** — 总览页能用，但用户明确反馈首屏不该放这个；把排障入口留在错误
  的位置，等于让它继续被忽略。

## Consequences

- 总览页少一张卡片、少一次 `/api/system/data-status` 往返；排障从两个点击变成三个。
- 非 admin 用户看不到这一页（总览对所有人可见；该接口本身仅要求登录，所以这不是
  权限收紧，只是入口可见性的变化）。
- 真源文件不再提供一键复制的 `mv`：少一次误删，多一步手动拼命令。

## Testing

- `npm run pipeline:image`：每个场景在容器内真实登录后打 8 个鉴权接口（含
  `/api/system/data-status`）必须全部 200 —— 这次搬动如果只改前端、接口挂了，
  会在这一步被抓到。
- 本地 `node bin/serve.js` 起服务后请求 `/app.js`，确认服务端下发的就是新前端
  （`renderSystem` 存在、nav 里有 `system`）。
