# Agent Note: 额度闸门的接管探测必须退避;拦截日志必须限频

Status: implemented

## Problem

用户问:[为什么它要轮询所有账号?哪怕账号额度不满足也还是轮询请求, 以及日志?
为什么不会直接跳过呢?这导致账号选择的时候很慢.]

复读选号链路后确认,用户看到的三个现象里**两个是同一个机制**,而且**排序那一步其实不慢**.

### 一,额度闸门根本不在候选排序里

- candidates.ts 的排序只做**排序**: 额度耗尽/买不起的账号被压到末尾
  (a.exhausted - b.exhausted, a.unaffordable - b.unaffordable),**不是被剔除**.
- 真正的额度闸门在**逐账号尝试**里(account-gates.ts),
  由 acquire.ts 的 for (const key of order) 逐个调用.
- 所以[逐个轮询 + 逐条日志]是**结构性的**: 每个请求都要把候选走完才能报错,
  而每个被额度拦下的账号都会 logger.info('skip account: ...').

### 二,慢的真正来源:每个请求对每个额度不足的账号各发一次 GET /session

两本额度账都由**会话回执缓存**驱动,并且都刻意 fail-open:

- 没有该模型的 units 行 / 没有 freebucks 块 -> known: false -> 不拦截;
- daily.resetAt 已过 -> stale: true, affordable: true -> 放行.

于是闸门命中是常态.而闸门命中会触发一次**真实的只读探测**
(makePaidUpstreamChecker -> rt.sessions.refresh(),即 GET /session),
用于发现[别的部署建的已付费会话](balance: 0 只说明[再买一条买不起]).

那个探测是**每请求每账号一次**:

- makePaidUpstreamChecker 的 state 是**每请求一份**的,请求结束即丢;
- refresh() 在**有在途请求**时会主动跳过探测(避免顶掉活跃会话),于是
  [用户正在用]这个场景下探测**几乎每次都失败**,而下一次请求又老老实实再发一次;
- 结果:池内 N 个额度不足的账号 x M 个在途请求 = N x M 次串行上游往返,
  全部发生在**首字节之前**.这是[选号很慢]的直接成因,与排序无关.
- 并列伤害:失败探测还会把 lastProbe 打成失败,控制台于是显示[探测失败/不可用],
  而账号其实只是没钱.

### 三,同邮箱被[轮询好几次]的机制

账号 key 是 Freebuff 用户 id(GitHub / Google 同邮箱各登录一次 = 两个独立账号),
列表里因此出现两行同邮箱. sticky 调度的平局规则是[最近用过的优先 + rotation
(即 this._rr 索引)],而 _rr 每次选号只 +1,于是**索引相邻的两个同邮箱账号会被连续
选中挨个试**,日志里就成了[同一个邮箱被轮询了好几次].

## Decision

### 一,接管探测要退避,窗口挂在 runtime 上

- runtime.paidProbeRetryAt(runtime 字段,不是请求级 state): **问过上游一次之后
  (不论成功失败)按 PAID_UPSTREAM_PROBE_RETRY_MS(60s)延后下一次探测**.
- 窗口**只挡"再问上游一次"这一跳**,不挡"用已经知道的结果": 本地快照
  (holderFor)先查且不受窗口约束.第一版把整个 checker 在窗口内短路成
  [没有可接管会话],评审指出这会把**已经付过钱的一小时**白丢 ----
  窗口内明明有可接管的持有者,却判成 freebucks_exhausted 去别的账号重买.
- 为什么[成功也要退避]: 成功且命中持有者时,下一个请求会为同一个持有者再探一次;
  命中那一刻已经拿到了要用的结果,窗口挡的是后续的重问.
- 窗口只挡重复探测,不挡首次 ---- 别的部署刚建的会话最多晚 60s 被发现.
- runtime 重建(改代理 / 换 token)时窗口归零:出口变了就该重新问一次.
- 探测失败从[抛给调用方]改为**降级**:按闸门结论继续,并记一条 warn.
  上游连不通时,把整池判成[买不起]比让请求卡在探测上更符合用户利益.

### 二,拦截日志按(账号, 拦截码)限频 60s

skipLogOnce(self, key, code, msg, fields): 窗口内沉默,窗口外再记一条,
首条带完整账目(余额/单价/日池).窗口表挂在账号池上,不进账本 ---- 它只是日志节流.
限频不丢信息:排障仍能看到[这个号是什么时候开始被挡的],这是 60s 粒度而非逐请求粒度.

### 三,同邮箱多身份在控制台标出来(不改 key 口径)

- 后端 readAccountUser 兜底扫描命中**多个**同邮箱文件时,旧行为是 return null ->
  调用方报 401 Account not found(账号在列表里却一个都用不了).改为**确定化**:
  key 精确 > 小写 key > 邮箱,同档按文件名升序,并记一条 warn.
- 列表行新增[同邮箱]徽章(同一邮箱在池内出现 >1 次时挂),消除[账号重复了/被覆盖了]的观感.

## Alternatives considered

- **把已知额度不足的账号从候选里剔除** ---- 看起来最直观,但会破坏两条既有语义:
  (1) [整池耗尽 -> freebucks_exhausted / units_exhausted 具名错误码]会退化成笼统的
  no_available_account(对[等每日池刷新]的用户是信息损失);
  (2) 接管探测**本来就是为[本地买不起但上游有已付费会话]设计的**,剔除候选等于
  把这条路径关掉.现有用例(quota.ts)也把[排到末尾]钉死为预期.
  真正的问题不是[试了],是[试的价格是 N 次上游往返].
- **什么都不做** ---- 保留现状.代价是每个请求 N 次串行 GET,且日志被 skip 行冲爆;
  用户已经在问[为什么这么慢],这个代价不可接受.
- **把探测降到只在控制台手动触发** ---- 会丢掉[别的部署建了会话时自动接管]的能力,
  那正是 reuse-paid-session 定下的行为.
- **按账号写[下次探测时间]到账本(持久化)** ---- 重启后仍生效,但把一个纯调度优化
  写进账本会引入落盘写放大与格式迁移;runtime 级窗口足够覆盖[高并发时段].
- **把 skip 日志直接降到 debug** ---- 默认(info)下完全看不见,排障时[什么时候开始被挡]
  就查不到了.限频保留了可观测性.
- **同邮箱账号合并成一个身份** ---- 会把两个独立的 Freebuff 账号(各自独立额度与冷却)
  合成一个,等于凭空丢弃一个号的额度.标注比合并正确.

## Consequences

- **额度不足的账号不再让每个请求付 N 次上游往返**: 一整池全买不起时,首轮之后
  (60s 窗口内)探测次数为 0.
- **探测退化路径**: 上游连不通时不再抛错,而是按闸门结论继续 -> 用户看到的是
  freebucks_exhausted(可操作:等刷新或加号)而不是一个不明所以的探测错误.
- **可接管的已付费会话最多晚 60s 被发现**: 窗口内不探测的代价.
- **日志量**: 池内 N 个账号同时额度不足时,每 60s 每账号最多 1 条 skip 行
  (此前每个请求每账号 1 条).

## Correction

用户问的是[为什么额度不满足也轮询].我第一轮回答把[逐个尝试]归因于排序没有剔除候选,
随后复核发现**排序并非瓶颈**(本地 Map 读,纳秒级),真正的代价是**探测那一次上游往返**.
本 note 记的是修正后的口径:不动排序语义,给探测与日志各加一道窗口.
