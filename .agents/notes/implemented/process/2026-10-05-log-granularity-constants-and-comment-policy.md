# Agent Note: 日志分两类颗粒度 + 常量集中 + 注释只写"做什么"

Status: implemented

受影响代码: `src/util/{log,log-kinds}.ts`、`src/shared/constants.ts`（新增）、
`dashboard/views/logs/index.ts`、全仓 `.ts` 注释、`scripts/gates/checks/style/comments.ts`（新增）、
`scripts/gates/checks/guard/tunable/literals.ts`（新增）、`scripts/gates/meta/comment/trim.ts`

## Problem

用户提了三条要求：

1. **日志颗粒度要分两类**：以「下游请求」为一粒（整条链路聚合成一次请求），
   以及独立「事件」（额度刷新 / 账号探测 / 模型获取 等）；且要有**跨语言标注**。
2. **全项目常量集中到一处**便于复用。
3. **注释必须简洁**：只写"这个函数做什么"；禁止写"为什么 / 决策 / 历史"——那些属于
   `.agents/notes/` 与 `docs/`；函数注释里要能链接到对应文件。

现状：日志只有 `ts/level/msg` + 请求上下文（有 `reqId` 的带上下文，其余是"无主记录"），
**没有"这是一次请求还是一次事件"这个维度**，也没有事件类型；前端日志页只能按 `reqId`
聚合，看不出"这条是额度刷新还是某个账号的探测"。常量散落（同一数值在多处写死）。
注释规模：受控 `.ts` 54200 行里 **14842 行是注释（27%）**，其中 886 处含"为什么/决策/历史"
类内容（292 个文件）——读代码的人要在一段事故复盘里找"这个函数做什么"。

## Decision

### 一、日志：`kind` + `event` 两个维度

- `src/util/log-kinds.ts` 是分类真源：`LogKind = 'request' | 'event'`；
  `EVENTS` 列 17 类事件，每类带中英双语文案（额度刷新/账号探测/模型获取/目录同步/导入/删除/
  登录/会话建立/释放/退款/保活/设备密钥/代理测试/设置变更/数据文件/系统/遥测）。
- 每条日志自动带 `kind`：**在请求上下文里 = `request`（带 `reqId`），否则 = `event`** ——
  这个判定不需要每个调用点声明，因此不会漏标。
- 新增 `logger.event(event, level, msg, fields)` 入口，供独立事件使用（已接 9 处）。
- `readLogBuffer` 支持 `kind` / `event` 过滤；前端日志页显示对应徽标，
  事件标签走 `logs.event.*` 词条（受 i18n 门禁校验）。
- 前端事件标签用**显式 key 映射表**而不是 `t('logs.event.' + key)` 拼接：拼接出来的 key
  静态扫描看不到，"词条缺失"会被漏过。

### 二、常量：单一模块 + 门禁

`src/shared/constants.ts` 收 `MS`/`SEC`（时间）、`LOG`（缓冲上限）、`HEADERS`（上游头名）、
`MODEL_HANDLE_PREFIX`、`DATA_FILES`（dataDir 下的文件名）。
新增门禁 `check-constants` 只拦**高置信度**字面量（小时/天的毫秒数、日志缓冲上限）——
误报比漏报贵得多，一条总在喊的门禁会被人关掉。`test/` 与 `cli-telemetry.ts` 按理由豁免
（那里的时长是夹具取值 / 单处语义，不是通用常量）。

### 三、注释：只写"做什么"，并由门禁守住

- 新增 `check-comments`：注释里出现解释性词元即违规，修复文案指向 notes/docs；
  引用 `.agents/notes/` 路径的注释豁免（那是指针，不是解释本身）。
- 词元表**收窄过一次**：初版把「否则 / 而不是 / 因为」也算上，但
  「必须带 instanceId，否则上游回 428」是**行为约束**，不是"为什么"。
  最终只留真正表示动机/历史的词（为什么/原因/决策/历史/教训/曾经/此前/旧实现/踩过/
  事故/实测/否决/权衡/代价/动机/源于/之所以）。
- 全仓清理：**886 处 → 0**（295 个文件改动），分批执行，每批都有"代码零改动"的自证。

## Alternatives considered

- **日志只加一个 `type` 字段**（不区 `kind`/`event`）。最强理由：一个维度最简单，
  前端一个下拉就能筛完。否决原因：两类东西的**聚合语义不同**——请求日志要按 `reqId`
  归组（一条链路），事件日志根本没有 `reqId`。合成一个字段会让"按请求聚合"这个操作
  要在前端猜哪些值属于请求。

- **让每个调用点显式传 `kind`**。最强理由：最准确，调用者最清楚自己在记什么。
  否决原因：189 个调用点要逐个判断，漏标就是静默的数据缺失（而那正是现状的问题）。
  改成"由是否在请求上下文里推导"之后，`required` 的判定自动化了，调用点只需在
  **独立事件**上显式写 `logger.event(...)`。

- **常量集中做成一个大 `constants.ts`（含端口/行数上限/超时秒数）**。最强理由：
  名副其实的"全项目常量一处定义"。否决原因：那些值**已经有配置真源**
  （`src/config/tunable/specs.ts` 的可调项表、门禁的 `rules.ts` 阈值）。
  再收一份就会出现"同一个值两个来源"，而它能赢取决于谁后加载。
  常量模块只收**没有配置入口、纯代码级**的复用值。

- **注释只警告不拦**（先观察一段时间）。最强理由：语义判据有误报风险，硬拦会挡人。
  否决原因：本仓已有先例——只警告的门禁在几周内就退化成背景噪音（i18n 的"死词条"
  提示至今没人清）。改法是**把词元表收窄到高置信度**，而不是取消拦截。

- **用模型做注释语义判定**。最强理由：能真正理解"这段是不是在讲原因"，比词元准。
  否决原因：CI 结果会不确定；而词元表可以被逐条列举、逐条解释，误报率可度量、可复现。

## 影响

- 日志：新增可筛选的 `kind`/`event` 维度与中英双语标签；旧的 `reqId` 聚合保持不变。
- 常量：`log.ts` 的 ringCap、`release/settle.ts` 的小时换算已改走常量真源。
- 注释：886 处清零；注释占比 27% → 25%。
- **零代码改动已逐字节证明**：对 295 个改动 `.ts` 用 TypeScript 的
  `createPrinter({removeComments: true})` 打印 HEAD 版与工作区版并比对，
  仅 2 个（本次新增的门禁与精简工具）有代码差异。
  这个比对抓到一个真实 bug：`session/handles/records.ts` 的 `refundKey()` 第一次编辑时
  `return` 那行被吞进上一行注释（`node --check` 能过，坏在运行期）——已还原。
- 测试与门禁：18/18 门禁 ALL PASS；`test/run.ts` ALL SUITES PASS（6 个，165.5s）；
  `typecheck` exit 0。
