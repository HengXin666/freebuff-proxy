# Agent Note: 探针会随门禁演进一起漂移

Status: implemented

受影响代码: `scripts/gates/probes/cases.ts`,`scripts/gates/probe-gates.ts`

## Problem

负向探针的作用是"证明门禁真的会红".但探针本身引用门禁的**输出文案,文件
路径,以及夹具规模**,这些都会随着门禁演进变化 -- 于是探针会在没人注意的
时候失去效力,而它的失效**看起来跟通过一模一样**.

2026-10-05 一次性暴露三条,形态各不相同,且都不是被保护代码的问题:

1. **lane 覆盖探针**:断言了输出里的文案片段,而 check-lanes 在"夹具里只有一个
   未认领条目"这种极小输入下走了另一条分支.退出码是对的(1),片段对不上.
2. **指纹接线探针**:它篡改的注册表路径写死为 `checks/code/lanes.mjs`,而该文件
   早已挪到 `checks/guard/lanes.mjs`.篡改目标不存在 → 指纹不变 → "应当 FAIL"
   变成 PASS.**这正是接线探针要防的那类漂移,发生在了探针自己身上.**
3. **语法控制组**:夹具只有 1 个文件,撞上了 syntax 门禁后来加的 `MIN_FILES=20`
   下界.下界断言在正确工作,但控制组测的就不是它想测的东西了.

## Decision

三条分别修,并固化两条口径:

- **探针的断言优先钉退出码,文案片段只钉"最稳定的那一句"**.文案是给人看的,
  会随可读性改动变化;退出码是契约.
- **夹具规模必须满足门禁的下界断言**.凡门禁有 `MIN_*` 下界的,配套夹具要么
  超过下界,要么显式说明"本探针就是在测下界本身".

改动(三轮, 都由 CI 实测驱动):

1. lane 探针去掉文案断言, 只钉退出码.
2. 指纹探针的篡改路径改为 `checks/guard/lanes.mjs`.
3. 语法**违规组**与**控制组**的夹具从 1 个文件扩到 26 个 -- 两个夹具都撞上了
   MIN_FILES=20 下界, 报出来的是"扫描面太小"而不是"语法不可解析".
   第三次是 CI 第二次失败才暴露的: 修了控制组, 漏了违规组.
4. 坏样本换成跨 Node 版本稳定的 `const a = {;`. 原来的
   `export function broken( {` 在 **node 22(CI) 被判为可解析**, 而 node 26(本机)
   判为语法错 -- 于是本地绿,CI 红. 夹具里的"坏输入"必须两端行为一致,
   否则它测的是 Node 版本而不是门禁.

原记录:
语法控制组夹具从 1 个文件扩到 25 个.

## Alternatives considered

- **什么都不做 / 让探针跑在 CI 里等它红**:最强的理由是"CI 会跑 `check:gates:probe`,
  红了自然有人修".否决原因:本次就是 CI 红了才发现的 -- 而它红了整整一个
  发布周期(`quality` job 在 v1.27.0 的 push 上失败).探针的失效必须在**本地
  提交前**可见,否则它只是一条延迟报警.
- **把探针也纳入 fingerprint**:最强的理由是"接线探针已经证明了指纹能防漂移".
  否决原因:指纹抽的是**门禁注册表与阈值**,而探针的失效来自**被断言的输出文案
  与夹具规模**--那是内容不是接线.把内容也抽进指纹会让每次改文案都要重录,
  报警器退化成确认键.
- **让探针只断言退出码,完全不管文案**:最强的理由是"最稳".否决原因:有一类
  失效是"退出码对了但理由错了"(例如把"语法不可解析"错报成"扫描面太小"),
  完全放弃文案就抓不到.所以保留**一句**最稳定的片段.

## Consequences

- 门禁新增/修改 `MIN_*` 下界,输出文案,或注册表路径时,**必须同时检查探针**.
  这条写进 `scripts/gates/probes/cases.ts` 的文件头.
- `npm run check:gates:probe` 现在是 `quality` job 的必过步骤;本次修复后
  22 条探针全部符合预期.
