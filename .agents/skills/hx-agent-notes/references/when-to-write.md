# 什么时候该写、该改、该移动一篇 note

## 判据

当一次改动触及行为、架构、跨文件或跨包的契约、流程与工具、测试策略,或者磁盘/线上/配置格式 —— 简言之,当维护者**有理由**回头重新审视它时 —— 就该写.

一句话判据:**半年后的读者会不会问"为什么不干脆用更简单的做法?"** 会,答案就属于这棵目录树.

拿不准?就当作需要写. 「这次很小」「代码本身就是文档」「以后再补」,正是这三条借口产出了一个谁都不敢改的仓库.

## 更新优先于新建

大多数 note 的改动都不是新文件. 当一个模块演进了但它的决策仍然成立时,**就地修正**那条拥有该决策的 note. 为同一条决策新建第二篇,会把理由劈成两个终将漂移的文件,而门禁的读者 —— 下一个 agent —— 只会找到其中一个,然后相信它.

## 判据矩阵

| 情形 | 动作 |
|---|---|
| 代码移动、改名或默认值变了,但决策仍然成立 | 就地更新该 note 的事实,与代码同一次改动 |
| 新方向,尚未实施 | 新建 `proposed/<class>`:动机、≥2 个真实备选、验收标准 |
| 工作已落地 | 在同一次提交里转为 `implemented/<class>`,现在时,并加上源码引用 |
| 提案在评审中失败 | `rejected/<class>`,理由写在状态行 —— 或者,如果没什么会诱人重犯,直接删掉 |
| 新决策部分取代旧的 | 两篇都留,互相链接,并把**仍然现行**的每个事实更新掉 |
| 新决策完全取代旧的 | 用 `notes:archive` 移走旧 note,把它仍然有用的理由并入新 note,修复入站链接 |
| 格式化、升级锁文件、打 tag | 不写 |

## 取代(supersession)

当一篇 note 被完全取代:

1. 通审旧 note,挑出任何独有的东西 —— 一条否定性保证、一条安全规则、一个"何时应当重新引入"的条件、一次它记录下来的失败.
2. 把这些材料搬进新 note. **从此归新 note 所有.**
3. 用 `notes:archive` 归档旧的:它会盖上 seal 行、报告入站链接、并重新封装 manifest.
4. 修复**每一条**入站链接:要么退役到当前的权威 note,要么 —— 当被引用的正是那段历史时 —— 重定向到归档后的路径.

第 4 步会被归档/反向引用门禁当作断裂引用抓出来,所以忘了修复会让 CI 变红,而不是悄悄烂掉.

## `proposed` 还是 `implemented`

当提案大到"应该先评审再动手",或者问题还没定的时候,从 `proposed` 开始. 决策已经拍板并上线了,就从 `implemented` 开始. **一个没有希望被推进的提案应当 rejected,绝不归档** —— 归档区是留给那些"指导价值已经过期"的已落地决策的.
