# 怎么写好一篇 note

两份清单: 前一半管**句子的形状**, 后一半管**意思有没有缺口**. 语义判断属于人, 不属于校验器

写 note 正文的时候加载这份

## 标准

**写到足以保住契约, 同时删掉产生它的那套推理.** 契约是一项义务、不变式、前置条件、后置条件, 或调用方与维护者所依赖的兼容性承诺

逐段保留每一个命题: 主体与动作、条件与时机、语气(`must` / `may` / `never`)、否定性保证与例外、归属、副作用、失败模式、后果. **只有当以上每一项都活下来时, 删字才是改进.**

## 一段话值得被怀疑的理由

对任何一句话都问:**只有 HEAD 上的仓库的人, 看得见这句话吗?** 如果它需要依赖这次对话、那个 PR、或者上一个版本来理解, 那就是泄漏

把序列提出来, 然后删掉产生它的脚手架  **推理留在结果里, 不留在纸面上.**

1. **悬空引用.** `(决策 7)`、`(审计 C2)`、某个没人手里的文档的 `§3.2`. 换成指向已提交 note 的相对 markdown 路径, 或者把事实本身重述一遍
2. **分支或 PR 视角.** 「本 PR 新增」「后续会」「上一个提交」. 陈述现在树里的机制, 或者留一个指明真实 issue 的 `TODO`
3. **变更叙述.** 「原先」「不再」「过去是」「现在」「被重写为」. 用现在时; 把回归表达成现在时的反事实  「没有 X 就会发生 Y」
4. **评审过场.** 「评审者确认了」「我们讨论后决定」「提案第 5 版」. 留下决策和它的理由, 去掉是谁、什么时候说的
5. **自我辩护.** 「这很安全, 因为它只在启动时用一次」. 陈述让它安全的那个不变式, 否则删掉这句话
6. **过程叙述.** 「我们先试了 X, 然后 Y」. 如果存在一个非显然的顺序约束, 保留它; 否则删掉
7. **含糊与占位.** 「应该够了」「大概没问题」「待定」. 要么升级成一条明确的边界、一个带署名的 `TODO`, 要么点名一个覆盖缺口
8. **语言混杂.** 半翻译的工作语言残片. 选定一种语言, 写完

**不算泄漏, 而且值得保留**: issue 引用、`TODO(name):`、note 内部对已合并 PR 的引用、抑制原因、现在时反事实、带测量方式的边界数字、已提交文档的编号章节.

## 矫枉过正的陷阱

删减有它自己的失败模式. 动手之前, 先列出这段话里的命题, 然后检查没有发生下面任何一条

- 一个 **must** 或 **never** 被软化成「你可以」 **约束变成了可选项**
- 一个**计划**或未决问题被删成了已落地事实  **提案现在读起来像已上线**
- 一句真话因为读起来像叙述而被删掉
- 出处跟着散文一起消失: 「测量:512 层 ≈ 0.15 s」丢了「测量」二字, 数字就没有来源了

## 结构性习惯

- **一个事实一个家.** 在它被拥有的地方陈述, 别处链接. 用一句有辨识度的短语 grep 一遍找重复
- 保留**可检索的机制名**和真实的语气词(`must`、`may`、`never`), 以及顺序约束和否定性强调. 装饰性强调要**归一化, 而不是全删**: 满篇加粗等于什么都不突出
- 宁可点出主体和动作, 也别用「这个契约」「那条边界」这类抽象  除非那确实就是技术主语
- 一段话里背了好几条规则的, 拆开, 或者把细节下放到它该在的地方

## 语义自检

脚本查的是结构, 这份清单查的是**意思**. 写完一篇 note 后跑一遍, 而且**只报缺口和真正站得住的部分**  最多五行, 绝不背清单

语义判断属于这里,**永远不属于校验器**: 一个会因为「动机不够强」判失败的脚本只会制造噪音, 而噪音会训练所有人无视门禁

## Problem

- 动机**脱离方案也能独立成立**: 把它后面全部删掉, 问题还是同一个问题
- 触发条件写清楚了  什么坏了、什么必须变、什么都不做会怎样

## Decision / Proposal

- 具体到**可以照着动手**. 「会话存储用 SQLite」, 不是「用个更好的数据库」
- 理由是**被对比逼出来的**: 每一个「决定了 X」都配一句「X 优于 Y, 因为 …」

## Alternatives considered

- 至少两个真实备选, 其中包含「什么都不做 / 复用已有的」
- 每个对手**最强的论据出现在它输掉的理由之前**. 只在最弱处被驳倒的对手是稻草人
- 落败的理由落在**具体的驱动条件**上, 不是「感觉不太对」

## Consequences

- **两半都要有**: 什么变难了, 什么变容易了. 只有好处的后果是被挑选出来的, 不是被观察到的
- 简化类决策要写明它的上限, 以及什么信号出现时该重新审视
- **没有基线就没有相对断言.** 没有实测对比的「更快」, 改写成陈述事实

## Verification

- 落在**可查的面上**: 哪条路径、多大数量级、哪条命令
- 不能有任何东西建立在「看起来是对的」上. 判据要么可查, 要么被显式地延后

## 汇报格式

```markdown
**语义自检: <文件名>**
站得住: <真正扎实的部分  动机、对手、代价>
缺口:
- Alternatives  「什么都不做」那条是稻草人;补上真正的对手和它最强的一面
- Consequences  「降低了延迟」需要一条路径和一个数量级,否则改成陈述事实
```

人类接受这些缺口, note 就这样发布; 或者先把缺口补掉. **这个判断不是脚本, 也不应该长成脚本.**

## 全库审计

里程碑式的全量审阅会读遍范围内的每一篇 note, 并按`mechanism.md` 的整理规则把它归入 保留 / 更新 / 合并 / 删除. **把同类 note 归到一个原则下判断, 而不是一个case一个case地判**; 不要以减少数量为目标删除; 每一个真正处在边界上的案例, 连它的推理一起报出来交给人类拍板

先看 note 们自己引用到的那些候选路径, 然后再移交

1. 既没有入站链接、也没有源码引用的 note  检查其决策是否仍有效, 或补齐实现锚点
2. 前提在树里已经不存在的 `rejected/` note
3. 迟迟没有任何推进的 `proposed/` note

然后跑门禁、项目自己的测试套件, 以及 `git diff --check`

## 把规则接进项目

**Skill 只在 agent 已经决定要用它的时候才会触发.** 真正耐久的挂载点是项目自己的指令文件, 它每次会话都会被加载  把 [../assets/AGENTS.snippet.md](../assets/AGENTS.snippet.md) 拷进项目的 `AGENTS.md` 或 `CLAUDE.md`. 这份片段是**行为侧**的那一半; 门禁是**机械侧**的那一半. 两者谁也替代不了谁: 门禁能看见一篇 note 存在, 看不见它是否诚实; 而指令会在压力下被忘掉
